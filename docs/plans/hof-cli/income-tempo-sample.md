## 四、「资源保守策略 HP 掉得多」的归因

60 局样本里资源保守的净粮食不比别的策略少（都是 −5），但 HP 极差 −19。**但那 60 局里装备与消耗品是同时变的**（保守策略既少买装备、也买得少），所以那张表**不足以归因**。

受控四臂把它拆开：同 seed、同路线、同事件，只变【武器档】与【是否真的把药喝掉】。

| 臂 | 平均喝药瓶数 | 死亡 | 精英战前HP中位 | 精英战ΔHP中位 | 精英战ΔHP均值 | 终HP中位 | 终金币中位 |
|---|---|---|---|---|---|---|---|
| A 长刀（档3）·无药 | 0.00 | 0/20 | 20 | 0 | −1.75 | 18 | 22 |
| B 长刀（档3）·喝药 | 1.05 | 0/20 | 20 | 0 | −1.75 | 20 | 18 |
| C 短刃（档1）·无药 | 0.00 | **4/20** | 19 | **−8** | −7.50 | 11 | 25 |
| D 短刃（档1）·喝药 | 1.10 | **0/20** | 20 | **−8** | −7.60 | 12 | 21 |

**三条结论，各自有对照：**

1. **主因是武器档，不是省粮。** A 与 C 只差武器档（长刀 3 vs 短刃 1），精英战 ΔHP 从「中位 0」变成「中位 −8」，死亡从 0/20 变成 4/20。，因此 「省装备」的代价是**拿命垫**。
2. **喝药能救回死亡，但救不回挨打。** C→D 把死亡从 4/20 压到 0/20，终 HP 中位从 11 升到 12，但**精英战 ΔHP 中位仍是 −8**（挨的那一轮伤害没变，只是战前血池被垫高了）。
3. **喝药的钱是从金币收益里出的**：A→B 终金币中位 22 → 18（两瓶药 4 金币 = 2×2）。

**同 seed 逐局对照**（证明这不是聚合出来的假象）：

| seed | A 长刀·无药 ΔHP／终HP | B 长刀·喝药 | C 短刃·无药 | D 短刃·喝药 |
|---|---|---|---|---|
| 0 | 0／20 | 0／20 | −18／**0（死亡）** | −18／2 |
| 10 | 0／16 | 0／20 | −15／**0（死亡）** | −16／4 |
| 17 | 0／20 | 0／20 | −14／**0（死亡）** | −15／5 |
| 18 | −5／15 | −5／15 | −19／**0（死亡）** | −19／1 |

，因此 「省装备＝拿命垫」在**同一 seed 的同一场精英战**上成立，不是不同局之间的凑数。

**本节的方法教训（不得重犯）**：本节的 v1 版本里 B/D 臂**买了药却从不服用**，于是 B 与 A、D 与 C 逐字节相同——等于用两对相同的臂证明「消耗品无效」。现在把「平均喝药瓶数」印进表头，该数为 0 的话本节就没有证明力；`--controlled` 在两条喝药臂平均瓶数为 0 时**直接退出码 1**。

## 五、seed 敏感性：60 局 ≈ 几个独立样本

三种策略**全部 20/20 胜利**。在有随机性的游戏里这是强信号，必须自查，不得用「60 局全胜」暗示统计显著。

| 策略 | 结局取值 | 路径种类 | 各路径局数 | 终HP极差 |
|---|---|---|---|---|
| 武器优先 | 胜利 | 2 | 16／4 | 12–20 |
| 防护优先 | 胜利 | 2 | 16／4 | 15–20 |
| 资源保守 | 胜利 | 2 | 3／17 | 1–20 |

**自查结论（照实写，不作美化）：**

1. **胜负对 seed 完全不敏感**：60 局结局**全为胜利**，三种策略各自只有 1 种结局。，因此 「60 局全胜」**不构成统计证据**，它只说明**这条路线在此参数下不会输**。真实信息量约等于「三策略各 1 局」。
2. **路径也只有 2 种**，且两条路径的差异**只有一步**：多一个「林地战斗」（16:4 或 17:3 的分布）。即 seed 只决定**林间判定是否转成战斗**，其余全同。
3. **真正随 seed 变的只有三处数字**：林间判定是否战斗（决定 +2 金币与 +4 HP 的有无）、伏击/精英战的伤害骰。金币净增量因此只有两个取值（武器优先 10 或 12；防护优先 9 或 11；资源保守 13 或 15）。
4.，因此**这批读数的价值不在样本量，在覆盖面**：它说明「崖道→林地」这条主路在给定参数下**稳定可通关**，且三策略的收支结构可复算。**它不能证明**沼泽／沙地／潮渠三条分支、死亡解锁护符后的开局、跨局累计的行为——那些不在本次分母里（见 §七）。

## 十、两种 pin 别混用（`check-refs` 的用法陷阱）

本仓有**两份**引擎 pin 声明件，各自服务一条产品线，且**互不等于**：

| 声明件 | pin | 谁用它 |
|---|---|---|
| `.github/engine-ref.json` | `fb20f2a2d70bd14831e90546165f531d0ca8870c` | babel（`babel-tests.yml`） |
| `stories/hof-cli/engine-ref.json` | `7f9ef4ea8b98a636445a526ac20a4f90d5fc49cc` | HoF CLI（`hof-cli-tests.yml`） |

`tools/check-refs.mjs` 核的是 `stories/babel/scenarios/scenarios.json` 里声明的**引擎 README 行号**，因此它**只属 babel 面**（`hof-cli-tests.yml` 的 `run:` 块里根本不调它）。拿 HoF CLI 的 pin 去跑它，会报三处具名红：

```
$ node tools/check-refs.mjs --engine <hof-cli pin 树> --require-symbols
  通过 48｜不符 3
  ✗ [span2-vermin-hp-ac-per-item] engine/README.md:50 不含其声明的符号
  ✗ [span1-animals-hp-ac-per-item] engine/README.md:49 不含其声明的符号
  ✗ [span1-herb-poultice-house-rule-use] engine/README.md:45 不含其声明的符号
  rc=1
```

根因是同一行号在两个 pin 上指向不同内容（`fb20f2a2:45` 是 `Basic Rules and Legal/equipment.md`，`7f9ef4ea:45` 是 `playing-the-game.md` —— README 的 SRD 目录表条目数随 pin 变化）。换到 babel 的 pin 上，同一条命令是 `通过 51｜不符 0`，rc=0。

**结论：这不是基线红，是用法错。** 记在这里的理由：它是**会被后人引用**的类型——「反正有人说是既有问题」然后跳过。真实的门状态以 CI 的 babel job 为准。

复跑（两条 pin 各自跑各自的面）：

```bash
git worktree add ~/tmp/engine-fb20 fb20f2a2d70bd14831e90546165f531d0ca8870c   # babel 面
git worktree add ~/tmp/engine-hof  7f9ef4ea8b98a636445a526ac20a4f90d5fc49cc   # HoF CLI 面
node tools/check-refs.mjs --engine ~/tmp/engine-fb20 --require-symbols        # ⇒ 通过 51｜不符 0
```
